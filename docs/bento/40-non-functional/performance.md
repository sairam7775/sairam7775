# Performance

## Target

| # | Requirement |
|---|---|
| F1 | **The app runs next to its database:** the Vercel functions and the Supabase project are in the same region (Tokyo), because one chat turn makes several database round trips |
| F2 | **The engine plans in milliseconds** and costs nothing per run (pure code, no network) |
| F3 | **The chat streams,** so the traveller sees text long before a long turn finishes. `/api/chat` may run up to 120 seconds, and a turn's model calls end by 75 seconds, so the reply is saved before the platform stops the function ([Bento Man (software)](../30-software/bento-man.md)) |
| F4 | **The seasonal scene doesn't re-blur every frame:** no `filter` or `backdrop-filter` on anything that moves. Heavy shapes stay still, and a hidden tab pauses all of its animation |
| F5 | **Fonts and art need no fetch at build or run time** (self-hosted fonts; the scenes and figure drawn in SVG and CSS; the animation player loaded only when needed) |
| F6 | **Page-load budgets (Core Web Vitals, at the 75th percentile of real visits):** Largest Contentful Paint under 2.5 s, Interaction to Next Paint under 200 ms, Cumulative Layout Shift under 0.1. Chat-response time: not set yet |
| F7 | **The first screen's text is painted at once:** it never starts at opacity 0. It settles by movement only (`.settle`); `.up` (fade and rise) is for what comes after it |
| F8 | **A page reads what it needs at once:** reads that need only the trip's id start together, a later read waits only for the data it needs, and the trip, its route, its days and its bookings are each read once in a render (the trip page and Bookings; the planned places are still read twice, for their names and for their booking needs) |
| F9 | **No request waits forever on the database:** every server-side Supabase client (`lib/supabase/timeout.ts`: the signed-in client, the service-role client, the proxy's session check, the email-link callback) gives a read 10 s and a write or RPC 15 s, then fails through the caller's usual error path. A cut-off read is not retried by postgrest-js. A write RPC that times out may have committed, so accepting a proposal or changing dates then says the outcome can't be confirmed, never that it failed ([proposals and diffs](../10-product/proposals-and-diffs.md)); a traveller never sees the timeout's own text |
| F10 | **The home page's first screen never waits on the sign-in check or a loader.** There is no `loading.tsx` at the root (each other section has its own, so their pages still show the loader). A visitor with no Supabase session cookie (or only an emptied one, which is how the proxy clears a session Supabase refused) is signed out for certain, since `getUser()` then answers without asking Supabase, so their page is sent whole in the first response (`mayHaveSession`, `bento/src/lib/supabase/session-cookie.ts`). With a session cookie, the page is sent at once too, and only what differs when signed in (the header link, the two sets of buttons, the signed-out notice) waits for `getUser()`, behind invisible stand-ins the size of the signed-in buttons. The cookie only ever chooses the signed-out version; being signed in is `getUser()`'s answer alone, and the proxy's check in front of private pages is unchanged |
| F11 | **The home hero's fonts are asked for in the HTML:** the Latin files of Zen Kaku Gothic New 400 and 500 and Zen Maru Gothic 900 are preloaded on the home page only (`bento/src/lib/fonts/hero-preload.ts`, sent as `Link` headers), the same URLs fonts.css uses, so the browser doesn't first meet them during the page's first layout. Nothing else is preloaded: each preload shares the connection with the stylesheet |

## How it's checked

- F1: the `x-vercel-id` response header includes `hnd1` (checked 13 November 2026).
- F2: engine tests run in milliseconds in `npm test`.
- F5: `npm run build` (no network fetch for fonts).
- F6: real visits report `web_vital` events (metric LCP, INP or CLS, its value and the browser's rating) to PostHog, only for visitors who allowed analytics (`lib/analytics/web-vitals.ts`, mounted in the root layout when the answer is yes). Nothing is sent from a document loaded as a shared plan (`/shared/…`), decided by the address the document loaded, so moving on to another page doesn't send them either (`loadedOnSharedPlan`). In the lab: Lighthouse, mobile, against a local production build (`next build` and `next start`).
- F7: `bento/src/app/first-paint.test.ts` checks that `.settle` has no opacity, is off under reduced motion, and is what each page's first text uses (home, app header, trips, plan, a trip and its vault, sign-in and sign-up, settings, legal and status pages).
- F8: by hand, with a local probe that logs each request to Supabase during a render (not in the repo). The trip page (`bento/src/app/trips/[id]/page.tsx`) waits on the sign-in check, then one round of reads (`readTrip`, `bento/src/app/trips/[id]/load-trip.ts`: the trip store's five, the chat, bookings, review, share, dismissed gaps), then the place names and the chat's cities, then the travel days, backgrounds and ticket needs together. The gap check (`gapsFrom`, `bento/src/lib/vault/store.ts`) takes the trip, route, days and bookings the page already read. Bookings (`bento/src/app/trips/[id]/vault/page.tsx`) reads the trip, route, days, bookings, rates and chat together. The graph is read once even when two loads start together (`loadGraph`).
- F10: `bento/src/app/route-loaders.test.ts` (no root loader; every other `page.tsx` has a `loading.tsx` in its folder or one above it) and `bento/src/lib/supabase/session-cookie.test.ts`: the cookie check; against the real Supabase client, no session cookie means no user and no request, and a session cookie means it asks; an expired session refused by Supabase, run through the real proxy, leaves no session for the page; and the check matches the cookie name `createClient` uses (`sb-<project>-auth-token`), so a changed name fails a test instead of drawing everyone signed out. By hand: the signed-out home's HTML has no Suspense boundary and no loader; signed in, the hero is in the first chunk and four small boundaries follow.
- F11: `bento/src/lib/fonts/hero-preload.test.ts`: at most three files, each a Latin face that fonts.css really uses, and exactly the weights the hero's heading, kicker and paragraph draw with (a font update or a hero change that leaves a preload for a file nothing draws fails a test, as long as the hero keeps those class names), asked for as a font in CORS mode (else it downloads twice), the build rule that turns a `?url` import into its URL limited to that query (a rule for every .woff2 also took over fonts.css's own urls, and the built stylesheet then pointed at node_modules paths), and the home page calling it. By hand, on a production build: the home response carries the three `Link: rel=preload` headers with the stylesheet's own URLs, other pages carry none, each font file is requested once, and Chrome logs no unused-preload warning.
- F3, F9: unit tests with a fake clock and fake providers (`bento-man/__tests__/deadline.test.ts`, the provider tests) and a server that never answers (`supabase/timeout.test.ts`). Not yet checked against a real stalled provider or database.

## Evidence

- `bento/vercel.json` (`"regions": ["hnd1"]`); the move on 12 November 2026 ([region move](../50-operations/supabase-region-move.md)).
- F7, 22 November 2026, Lighthouse mobile (simulated throttling), local production build, home page signed out, 5 runs each, medians: LCP 5.3 s → 4.5 s, element render delay 1.20 s → 0.85 s, FCP 1.85 s → 1.86 s (no change). The LCP element is still the hero paragraph. CLS went from 0 to about 0.02 on 4 of 5 runs: the hero text is now visible while its web font swaps in, so that shift now counts (still under the 0.1 budget). Sign-in already had LCP equal to FCP, so it showed no measurable change. Measured again after the font change (#113), main `af1e739` against this branch, 5 runs each, medians: LCP 4.19 s → 3.71 s, render delay 0.82 s → 0.61 s, FCP 1.23 s both; CLS 0.017 on 1 of 5 runs, 0 on the rest (one main run timed the loader as LCP and is the 1.23 s outlier).
- F10, 22 November 2026, Lighthouse 13.6 mobile (simulated throttling), local production build, home page signed out, 5 runs each, main `6eb3259` against this change, medians: LCP 3.41 s → 1.23 s (now equal to FCP, so under the 2.5 s budget), FCP 1.08 s → 1.23 s, element render delay (observed, unthrottled) 550 ms → 271 ms, CLS 0 → 0.018, TBT 206 ms → 135 ms, score 0.88 → 0.99. The LCP element is still the hero paragraph. The cause was not the sign-in check: signed out, `getUser()` makes no request, and the whole page was sent in 24 ms. It was the root `loading.tsx`: the first response carried the loader, and React's reveal script swaps a streamed page in no sooner than 300 ms after the loader paints. FCP is later because the first paint is now the page itself rather than the loader. The CLS is the hero's web-font swap (Lighthouse names the font), counted now because the hero is on screen while the font loads (see Known gaps). Signed in (test account), same build: the hero comes in the first chunk (63–92 ms locally, the proxy's `getUser()` included) and the account's link, buttons and greeting about 20–30 ms later; no layout shift recorded in the browser.
- F8, measured 22 November 2026 on a local production build against the Tokyo project, a test account's trip with three cities: the trip page went from 21 requests to Supabase in 13 waits one after another to 17 requests in 5 (6 in a few renders, when one read finished early), and its median render from 600–680 ms to 440 ms. Bookings went from 14 requests in 7 waits to 11 in 5, and from 490 ms to 340 ms. One machine, shared with other work, so the times are rough; the request counts are exact.
- F11, 23–24 November 2026, local production builds of main `a9abaec` and this change served side by side, home page signed out, measured in alternating rounds (main, then the change) because the machine was shared with other builds and tests (CPU 38–82% busy, Lighthouse benchmark index about 430 against about 1,900 on a quiet run), so the absolute times are slow and only the comparison counts.
  - **Cause.** The live evidence (Lighthouse 12, LCP 2.4–3.2 s, render delay 1.6–2.55 s) is not a second paint when the font arrives: the paint traces show one LCP entry, the hero paragraph's first paint, equal to FCP. Lighthouse 12's simulation counts every request started before that paint, scripts and all 18 font files included, as needed for LCP (Lighthouse 13 uses the FCP estimate when a text LCP equals FCP). In a real throttled load (Chrome with 4× slower CPU and a slow-4G connection) the hero fonts were found only during the first layout, after the stylesheet, and arrived after the first paint, so the hero drew in the system font and moved when they swapped in (CLS 0.018); that first layout was 1.1–2.4 s long at 4× CPU, and roughly 0.25 s less with no web fonts at all.
  - **Real throttled loads** (Chrome, 4× CPU, 562 ms round trip, 1.47 Mbit/s, 7 rounds each, medians): LCP (equal to FCP in every run) 5.58 s → 4.94 s, CLS 0.018 → 0, hero fonts arrived at 3.63 s → 1.53 s (before the first paint).
  - **Lighthouse 12.8.2 mobile, simulated** (7 runs each, medians): LCP 3.16 s → 3.57 s, element render delay 2.70 s → 3.10 s, FCP 1.85 s → 2.03 s, CLS 0 both, TBT 613 → 414 ms, score 0.76 → 0.81. The simulation got worse: it starts the preloads beside the stylesheet and charges them to the first paint, and it doesn't model the shorter layout. It still counts every request before the paint, so it stays over 2.5 s whatever the fonts do.
  - Tried and not kept: a size-adjusted fallback face (`local(Arial)`) removed the shift but not the delay, and with the preloads it was slower; preloading only Kaku 400 left the heading's shift; Kaku 400 and Maru 900 alone was measured only while the machine was much busier, so it wasn't compared fairly and the three files tested first were kept.

## Known gaps

- **The home page met the LCP budget in the lab only under Lighthouse 13, signed out (F10, LCP equal to FCP); not yet confirmed by real visits** (no `web_vital` data yet). Lighthouse 12's simulation and the slow throttled loads in the F11 entry are both over 2.5 s. Signed in, it was checked only on a fast local connection: the stand-ins are the size of the signed-in buttons, but the greeting beside them isn't held, so on a narrow screen a long name that wraps to a second row would push the note below it down when the check is slow. Holding a second row instead would move the note up for every short greeting, the usual case, so it isn't held.
- **Lighthouse 12's simulated LCP stays over 2.5 s on the home page** (3.6 s locally with F11, 2.4–3.2 s live before it) although the real paint is the first one: it charges every request before the paint (about 190 KB of scripts and 18 font files) to LCP. Fewer bytes before the first paint would move it; the preloads don't. Real visits (`web_vital`) are the measure that counts.
- **The hero can still shift when its fonts arrive after the first paint** (a slower connection than the one tested, or a preload the browser drops); CLS was 0.018 then, under budget. A size-adjusted fallback face would cover it, but it was slower in the test above, so it isn't used.
- The real-load test ran Chrome on Windows only; not checked on an Android phone or Safari.
- **Real-visit numbers are per hard load:** one LCP, INP and CLS for each document Bento loads, not for each page reached by moving inside the app. None yet: `web_vital` events start with this change, and only from visitors who allowed analytics.
- A trip and its vault (signed-in pages) use `.settle` on their headers but were not measured in Lighthouse.
- Admin pages still show a database error's own text, a timeout's included ("AbortError: Supabase request timed out …"), and the service role has no statement timeout of its own, so an admin write or a spend hold that times out may still commit. A spend hold that commits late stays on the books until it ages out: the safe direction.
- A chat tool that makes several database reads can still take a turn past 120 s if two of them stall: each read is bounded, the tool is not.
- The time limits bound one slow dependency, not several at once. If the session refresh, the spend holds and the save all stall in one turn, the limits add up and can pass 120 s. supabase-auth may also retry a stalled token refresh once more, within its own 30 s window. The 15 s write limit assumes Supabase's default 8 s statement timeout for signed-in requests, which was not checked on the live project. Without it, a slow RPC could commit after the client gave up, and the page would show a failure until it is reloaded.
- No chat-response target.
- The Gemini free tier allows about 20 requests a day per model; heavy use moves down the fallback list ([Bento Man (software)](../30-software/bento-man.md)).
